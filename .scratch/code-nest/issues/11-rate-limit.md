# 限流防刷

Type: grilling
Status: resolved
Blocked by:

## Question

限流用什么算法（Redis + Lua 滑动窗口 vs 令牌桶）、以什么维度（用户/IP/接口）、如何以注解形式声明在接口上、哪些接口需要（发文、评论、点赞、登录）、被限流时的响应？

## Answer

1. **算法：滑动窗口日志**。
   - 每个限流 key 对应一个 ZSet，member 是请求 ID，score 是时间戳。
   - 用一段 Lua 脚本原子地完成四步：`ZREMRANGEBYSCORE` 清掉窗口外的记录 → `ZCARD` 统计窗口内请求数 → 未超限就 `ZADD` 记下本次请求 → `PEXPIRE` 设置 key 过期。
   - 时间取自脚本内的 Redis `TIME`，不用应用服务器的时钟，这样多实例之间的时钟偏差不会影响判断。
   - 选这个算法的原因：被限流的都是低频写操作，精确比平滑更重要，而且每个 key 的 ZSet 很小。固定窗口在窗口交界处会出现两倍突刺；令牌桶的参数不如"每分钟 N 次"直观。面试时可以对比这三种算法。
2. **限流维度**：
   - 需要登录的接口按用户 ID 限流。
   - 匿名接口（注册、登录、搜索）按 IP 限流。IP 默认取 `remoteAddr`；只有当请求来自配置中的可信代理（如压测时的 Nginx）时，才读取 `X-Forwarded-For`。
3. **注解**：`@RateLimit(key, limit, window, dimension)`。
   - 注解可以重复标注，从而同时限制短期和长期频率，例如"每分钟 10 次"加"每天 200 次"。
   - 由一个 `HandlerInterceptor` 处理，注册在 `SaInterceptor` 之后，这样登录校验完成后才开始限流，也就能拿到用户 ID。
   - 不用 AOP 实现。
4. **限流接口与默认限额**（全部可配置）：

   | 接口 | 维度 | 限额 |
   |---|---|---|
   | 注册 | IP | 5 次/小时 |
   | 登录 | IP | 10 次/分钟 |
   | 发布文章 | 用户 | 10 次/小时 |
   | 评论、回复 | 用户 | 10 次/分钟，且 200 次/天 |
   | 点赞、收藏（含取消） | 用户 | 60 次/分钟 |
   | 关注、取关 | 用户 | 30 次/分钟 |
   | 搜索 | IP | 60 次/分钟 |

   总开关是 `rate-limit.enabled`，压测时关闭。
5. **响应与降级**：
   - 超限时返回 HTTP 429，body 里是通用错误码"请求过于频繁"，并带上 `Retry-After` 响应头，值根据 ZSet 中最早一条记录的时间计算。
   - Redis 不可用时放行请求，同时打告警日志（fail-open）。
