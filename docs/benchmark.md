# 压测报告

四个主打亮点各保留"基线"与"优化"两套实现，用配置开关切换，在同一套环境、同一份数据上压测对比。每个亮点按 STAR 组织：S 场景、T 任务、A 方案与取舍（链接到决策票）、R 压测数据。

> 压测在一台机器上完成，各容器限定了 CPU 与内存，k6 与被测系统共用宿主机。**这里关注的是同一环境下优化前后的相对提升，不是绝对性能。**

## 测试环境

- **机器**：18 核、15G 内存，WSL2。
- **部署**：2 个应用实例，前面一个 Nginx 轮询；中间件 MySQL 8.4、Redis 8.6、RabbitMQ 4.3、Elasticsearch 9.4（IK 分词）。

  | 服务 | CPU | 内存 |
  |---|---|---|
  | 应用（每个实例） | 2 核 | 1.5G（`-Xmx1g`） |
  | MySQL | 2 核 | 2G（`innodb_buffer_pool_size=1G`） |
  | ES | 2 核 | 2G（堆 1g） |
  | Redis | 1 核 | 1G |
  | RabbitMQ | 1 核 | 1G |
  | Nginx | 1 核 | — |
  | k6 | 不限，用剩余的 CPU | — |

- **数据**：固定随机种子造数。10 万用户、10 万篇文章（已发布 94,851 篇）、500 万条关注关系、199 万条点赞、57 万条评论与回复；10 个大 V 各 2 万粉丝，100 个重度用户各关注 500 人。
- **方法**：每一档先清空 Redis、重启应用；每轮先等 MQ 队列清空（最早跑的 A、B、C、D 四组在加入这一步之前，其中 B 修复前的一组和 C 受到场景 A 积压消息的影响，见各节），预热 30 秒，再稳态压测 2 分钟，压测前后各采集一次 MySQL `SHOW GLOBAL STATUS` 与 Redis `INFO commandstats` 取差值。每档跑 3 轮，各项指标分别取中位数。压测时关闭限流。
- **开关**：每个场景只切换被测的开关，其余开关默认停在基线档。场景 B、D 另在计数优化档（`counter.mode=redis-async`）下补测一组，原因见各节。
- **复现**：环境、造数与脚本见 [code-nest-loadtest/README.md](../code-nest-loadtest/README.md)；原始结果在 [code-nest-loadtest/results/](../code-nest-loadtest/results/)。

## A 计数系统

**S**：热门文章被大量用户同时点赞。每次点赞除了插入一行点赞关系，还要给文章点赞数、作者获赞数各加 1，这两行是所有点赞共享的热点行。

**T**：点赞接口在高并发下保持低延迟；每个用户对同一篇文章至多点赞一次，计数最终与点赞行数完全一致。

**A**（[计数系统决策票](../.scratch/code-nest/issues/06-counter-system.md)）：

- 瓶颈判断：点赞关系每次插入的是不同的行，不会争锁；真正排队的是 `UPDATE article_stat SET like_count = like_count + 1` 这类热点行更新。所以关系表仍同步写库，只把计数移出事务。
- 业务模块在自己的事务里调用 `CounterApi.increment`，经 Outbox 发出计数事件，提交后投递到 MQ；counter 模块不依赖任何业务模块。
- 消费端用一段 Lua 在 Redis 里原子完成：Hash 不存在返回 MISS（从 MySQL 懒加载后重试）→ 按 messageId `SET NX` 去重 → `HINCRBY` → 加入待落库集合。
- 每 5 秒 `SPOP` 一批待落库对象，把 **绝对值** 批量 `INSERT … ON DUPLICATE KEY UPDATE` 写回 MySQL；重复写结果不变，同一对象的多次变更合并成一次写入。
- 由掌握真实数据的模块每周对账，修正 Redis 与 MySQL。
- 取舍：放弃"计数与点赞在同一事务里强一致"，换来热点行不再排队；计数有秒级延迟；Redis 数据丢失时，尚未落库的增量（最多约 5 秒）靠对账补回。

**R**：200 个 VU 用 200 个账号对同一篇文章反复点赞、取消。

| 指标 | sync-db | redis-async | 变化 |
|---|---|---|---|
| QPS | 256 | 553 | +116% |
| 平均延迟 | 776ms | 360ms | −54% |
| P95 | 892ms | 779ms | −13% |
| P99 | 1000ms | 1009ms | 持平 |
| 错误率 | 0 | 0 | |
| `Innodb_row_lock_waits` | 34,341 | 1,435 | −96% |
| 行锁等待总时长 | 2,221s | 42s | −98% |
| Redis 命令 / 请求 | 2.0 | 14.2 | 计数移到 Redis |

- **正确性**：每轮压测结束、落库完成后，文章的 `like_count` 与点赞行数 `COUNT(*)` 都相等（6 轮全部通过）。
- **瓶颈转移**：sync-db 下两个应用实例各只用约 0.5 核，请求都在等行锁；redis-async 下应用实例跑满 2 核，MySQL 也升到约 2 核。吞吐翻倍，但瓶颈变成了应用 CPU（点赞仍要同步写点赞行和 3 条 Outbox 记录并投递消息，取消点赞 2 条），所以尾延迟没有随之下降。

## B Feed 推拉结合

**S**：用户读关注 Feed。纯拉模式下，关注的人越多，读 Feed 越慢；纯推模式下，大 V 每发一篇文章都要写入几万个粉丝的收件箱，形成写扩散风暴。

**T**：关注了几百人的重度用户读 Feed 首页依然快；大 V 发文不受粉丝数影响，普通作者发文后粉丝很快能看到。

**A**（[Feed 推拉结合决策票](../.scratch/code-nest/issues/07-feed.md)）：

- 普通作者发文推送到粉丝的收件箱（Redis ZSet，上限 500 条），大 V（粉丝数 ≥ 5000）不推送，读 Feed 时从他的发件箱（最近 100 篇）拉取；两路合并、按文章 ID 去重倒序。
- 收件箱 TTL 7 天、读取时续期；推送跳过收件箱已过期的冷用户，用户回来时从关注的普通作者的发件箱重建，不需要另外维护活跃用户名单。
- member 与 score 都是雪花文章 ID，ID 本身就是分页游标；score 是 double，大 ID 舍入后相同的一组按 ID 精确比较，翻页不重复、不遗漏。
- 关注、取关、删文时尽量修正收件箱与发件箱，修正不到的残留在读取时过滤。
- 识别大 V 读 social 维护的 ZSet `feed:followers`（作者 ID → 粉丝数，关注、取关后按关注表重新统计，启动时缺失就重建）：一条 `ZRANGEBYSCORE` 取出全部大 V，再与关注列表求交集。
- 取舍：推送是异步的，发文到粉丝可见有百毫秒级延迟；作者跨过大 V 阈值时不迁移历史数据；Feed 最多往回翻约 500 条。

**R**：200 个 VU 轮流使用 100 个重度用户（各关注 10 个大 V 和 490 个普通作者）读 Feed 首页；推送耗时是一个有 4999 个粉丝的普通作者（比阈值少 1）发文后，ID 最大（最后被推送）的粉丝读到这篇文章的时间。

| 指标 | pull | push-pull | 变化 |
|---|---|---|---|
| QPS | 605 | 791 | +31% |
| 平均延迟 | 330ms | 252ms | −24% |
| P95 | 1187ms | 862ms | −27% |
| P99 | 1670ms | 1173ms | −30% |
| 错误率 | 0 | 0 | |
| MySQL 读取行数 / 请求 | 1,062 | 557 | −48% |
| 推送 4999 个粉丝的耗时 | — | 148ms（三轮 104–237ms） | |

计数优化档（`counter.mode=redis-async`）下同样补测了一组，结论一致：pull 577 → push-pull 794 QPS（+38%），P99 1723ms → 1365ms（−21%），推送耗时 151ms。

- pull 用一条 `author_id IN (…500 个…) ORDER BY id DESC LIMIT 21` 在 MySQL 里归并 500 个作者的文章；push-pull 改读 1 个收件箱和 10 个大 V 的发件箱，省掉这条归并查询，MySQL 读取行数减半（剩下的主要是关注列表的 500 行）。
- **压测中发现并修复的瓶颈**：第一版识别大 V 时，逐个读取关注的约 500 个作者的粉丝数（sync-db 档是一条 500 行的 `IN` 查询，redis-async 档是约 520 条 `HMGET`），push-pull 反而比 pull 慢：sync-db 档 332 vs 575 QPS（这组压测期间场景 A 积压的通知仍在消费，两档同样受影响），redis-async 档 258 vs 530 QPS、每个请求 535 条 Redis 命令，两个应用实例跑满 2 核。改为读 `feed:followers` 后，每个请求的 Redis 命令降到 15 条（redis-async 档 35 条，多出的是读文章计数的 `HMGET`），push-pull 的 QPS 提升到修复前的 2.4–3.1 倍，反超 pull。修复前的原始结果保留在 `*-b-feed*-before-fix.json`。
- 读 Feed 首页仍有 P99 1.2 秒左右：两个应用实例基本跑满 2 核，瓶颈在应用 CPU（每页要解析 500 个关注的作者、合并 11 个 ZSet、组装作者与计数）。

## C 搜索与数据同步

**S**：10 万篇文章里按关键词搜索，基线是对标题、摘要、正文做 `LIKE '%kw%'`。

**T**：搜索延迟与文章总量解耦；结果按相关度排序、有高亮；文章发布、编辑、删除后秒级反映到搜索结果。

**A**（[搜索与数据同步决策票](../.scratch/code-nest/issues/08-search-sync.md)）：

- 同步走 Outbox + MQ：search 模块收到文章事件后，经 `ArticleApi` 回查最新状态再写入或删除 ES，天然解决事件乱序。
- 以 `article.version` 作为 ES 外部版本号，旧版本的写入被 ES 拒绝，防止并发消费时旧数据覆盖新数据。
- 写入用 `ik_max_word`、查询用 `ik_smart`；`multi_match` 标题权重 3、摘要 1.5、正文 1，关键词与标签名一致时再加分。
- 索引经别名访问，全量重建时建新索引、切别名、按 `updated_at` 追补，搜索不中断。
- 取舍：不用 Canal，避免多部署一个中间件、也避免 search 模块依赖 article 的表结构；作者昵称和计数不进 ES，展示时再补全。

**R**：50 个 VU 匿名搜索，关键词从技术词库随机抽取。

| 指标 | mysql-like | es | 变化 |
|---|---|---|---|
| QPS | 1.7 | 136 | 81 倍 |
| 平均延迟 | 28.3s | 366ms | −98.7% |
| P95 | 46.9s | 603ms | −98.7% |
| P99 | 52.1s | 696ms | −98.7% |
| 错误率 | 1.9% | 0 | |
| MySQL 读取行数 / 请求 | 180,202 | 40 | −99.98% |

- mysql-like 的错误全部是超过 60 秒的请求（Nginx 与 k6 的默认超时都是 60 秒）。`LIKE '%kw%'` 无法走索引，每次搜索扫描约 18 万行（文章表与正文表），MySQL 的 2 核被扫表占满。
- es 三轮的 QPS 分别是 80、136、179。前两轮压测期间，场景 A 的点赞产生的通知消息仍在消费、占用 MySQL；第 3 轮没有干扰，QPS 179、P99 481ms。表中取中位数，是偏保守的值。

**相关度抽查**：环境空闲时，两档各搜 10 个关键词，看前 5 条结果。

| 关键词 | mysql-like：命中数 / 前 5 条标题含关键词 | es：命中数 / 前 5 条标题含关键词 |
|---|---|---|
| 线程池、分布式锁、缓存穿透、倒排索引、MVCC、消息队列、虚拟线程、领域驱动设计（8 个） | 各约 3.9 万 / 0 条 | 各 1 万以上 / 5 条 |
| Redis 分布式锁 | 0 / — | 1 万以上 / 5 条 |
| 垃圾回收 调优 | 0 / — | 0 / — |

- mysql-like 没有相关度，按发布时间倒序，关键词大多只出现在正文里，前 5 条标题都不含关键词；多个词的查询要求整个字符串（含空格）原样出现，所以搜不到。
- es 按相关度排序，标题命中权重最高，前 5 条的标题都含关键词；`Redis 分布式锁` 分词后要求两个词都出现，找到的都是同时讲两者的文章。`调优` 不在造数词库里，两档都搜不到，符合预期。
- es 的命中数显示为 1 万以上，是 ES 默认只精确统计到 10,000 条。

## D 多级缓存

**S**：文章详情是读多写少的热点接口，访问高度集中在少数热门文章上。

**T**：热点文章的读取不打到 MySQL，同时处理好缓存一致性，以及穿透、击穿、雪崩这三类问题；多实例下各实例的本地缓存能及时失效。

**A**（[多级缓存与缓存治理决策票](../.scratch/code-nest/issues/09-multilevel-cache.md)）：

- 文章详情（元数据加正文，不含计数）用 Caffeine + Redis 两级缓存；用户、文章的批量摘要只用 Redis，批量读取走 `MGET`。缓存里不放计数，点赞不会让文章缓存失效。
- 业务代码只经 `TwoLevelCache` 的 `get`、`getAll`、`evict` 三个方法访问缓存，两级读取、空值缓存、布隆过滤器、TTL 抖动、失效广播都封装在组件内部。
- 一致性用 Cache-Aside：事务提交后删 Redis 并经 Pub/Sub 广播本地缓存失效，再由 MQ 消费文章事件做第二次删除，MQ 的投递延迟起到"延迟双删"的作用。
- 穿透用 Redis 8 原生布隆过滤器加 60 秒空值缓存；击穿靠 Caffeine 的同 key 合并加载，同一时刻落到数据库的查询数不超过实例数，不引入分布式锁；雪崩靠 TTL 加 0–5 分钟随机抖动。
- 取舍：热点 key 交给 Caffeine 的 W-TinyLFU 自然留存，不做专门探测；本地缓存以 60 秒 TTL 兜底 Pub/Sub 漏收。

**R**：300 个 VU 匿名访问文章详情，候选为最新发布的 1000 篇，按 Zipf 分布（指数 1.2）抽取，前 10 篇约占 57% 的请求。

先按"只切缓存开关、计数停在 sync-db"跑了一组，三档的 QPS 都在 415–584 之间，缓存看不出效果：

| 指标（计数 sync-db） | none | redis | two-level |
|---|---|---|---|
| QPS | 584 | 425 | 415 |
| P99 | 1716ms | 1647ms | 1896ms |
| MySQL 查询 / 请求 | 8.1 | 2.1 | 2.1 |
| 行锁等待 | 21,820 | 15,971 | 15,417 |

原因是每次打开文章都要浏览量 +1。sync-db 档下这是一条 `INSERT … ON DUPLICATE KEY UPDATE`，Zipf 分布让请求集中在 10 篇文章的计数行上，又回到了场景 A 的热点行排队：缓存把 MySQL 查询减少了 74%，但请求仍排在计数行的行锁上，redis、two-level 两档下两个应用实例各只用到约 0.5 核，MySQL 也只有约 0.6 核。所以在计数优化档（`counter.mode=redis-async`，浏览量直接 `HINCRBY`）下补测一组，单独看缓存的效果：

| 指标（计数 redis-async） | none | redis | two-level |
|---|---|---|---|
| QPS | 1,328 | 3,882（+192%） | 3,392（+155%） |
| 平均延迟 | 225ms | 77ms（−66%） | 88ms（−61%） |
| P95 | 682ms | 212ms | 280ms |
| P99 | 894ms | 347ms（−61%） | 480ms（−46%） |
| 错误率 | 0 | 0 | 0 |
| MySQL 查询 / 请求 | 6.03 | 0.01 | 0.01 |
| `Com_select` | 963,519 | 5,267（−99.5%） | 5,287 |
| 文章详情的 Redis `GET` | — | 466,020 | 3,771（−99.2%） |
| Redis 命令 / 请求 | 5.3 | 7.1 | 6.2 |

- **redis 档**：热点文章几乎不再查 MySQL，QPS 接近 3 倍，P99 降 61%。瓶颈转移到应用 CPU（两个实例跑满 2 核），MySQL 基本空闲，Redis 约 0.4 核。
- **two-level 档**：本地缓存命中后不再访问 Redis，文章详情的 Redis 读取减少 99.2%。但它没有带来更高的 QPS：详情只是每个请求约 7 次 Redis 调用中的 1 次（其余是浏览量计数、批量读计数和作者信息），单机容器之间的 Redis 往返不到 1 毫秒，Redis 也不是瓶颈；三轮之间的波动（2,028–3,840）大于两档之间的差距。本地缓存的价值在于分担 Redis：当 Redis 被多个实例共同压满、或者跨机房往返延迟较高时，它才会体现为吞吐和延迟的提升。
- 两组压测中两级缓存都覆盖了多实例场景：两个实例各有一份本地缓存，失效靠 Pub/Sub 广播。

## 关注列表缓存：30% 规则

**规则**（[压测方案决策票](../.scratch/code-nest/issues/12-load-test.md)）：在 push-pull 模式下，如果查询关注列表的耗时占 Feed 读取耗时的 30% 以上，就加一层 Redis Set 缓存（关注、取关时维护）；否则不加。

**测量**：Feed 读取在服务端记两个 Micrometer Timer：`feed.read`（读一页 Feed 的全部耗时）和 `feed.read.follow-list`（其中查询关注列表的耗时）。压测前后各读一次两个实例的累计值，取差值相除。

| 计数档 | Feed 读取平均耗时 | 关注列表查询平均耗时 | 占比（三轮） |
|---|---|---|---|
| sync-db | 225ms | 61.7ms | 27.5%（27.7% / 27.4% / 27.5%） |
| redis-async | 230ms | 4.9ms | 2.1%（2.1% / 2.2% / 1.9%） |

**结论：不加缓存。**

- 两种配置都低于 30%。
- 查询本身很便宜：它走 (follower_id, author_id) 唯一索引的覆盖扫描，MySQL 空闲时只要约 5ms。sync-db 档的 61.7ms 大部分是排在计数读写之后等连接、等 MySQL 的时间，缓存关注列表治标不治本，计数移到 Redis 后它自然降到 2%。
- 加缓存要在关注、取关时维护一份 500 个成员的 Set，并处理缓存与关注表的一致性，收益不抵复杂度。

## 已知缺陷

以下是方案有意接受的取舍，压测中没有观察到，但需要如实说明：

- **计数 SPOP 窗口**：落库任务 `SPOP` 取出待落库对象后、写入 MySQL 前实例崩溃，这批对象的待落库标记会丢失，它们在 MySQL 中停在旧值，直到下次变更或每周对账时修正。Redis 本身开启 AOF everysec，Redis 宕机最多丢约 1 秒的增量。
- **对账 ±1 误差**：对账先 `GROUP BY` 统计真实值再 `reset`，两步之间如果有并发的点赞或取消，结果可能差 1，下一次对账修正。
- **Cache-Aside 竞态**：读请求未命中后从数据库读到旧值，写请求在此期间更新数据库并删除缓存，读请求随后把旧值回填。窗口极小，经 MQ 的第二次删除可以覆盖大部分情况，最坏情况持续到 TTL（30 分钟加抖动）过期。
- **Pub/Sub 漏收**：本地缓存的失效靠 Redis Pub/Sub 广播，不保证送达；漏收的实例继续使用旧值，最多 60 秒（Caffeine 写入后过期时间）。
- **大 V 判定可能短暂偏差**：`feed:followers` 在关注、取关后按关注表重新统计写入，两个消费者并发修正同一个作者时，后写入的可能是先统计出的旧值。只在粉丝数恰好跨过阈值时影响大 V 判定，到这个作者下次被关注或取关时纠正。
- **Feed 某一页少于 size 条**：收件箱里可能残留已删除的文章、已取关作者的文章，读取时截取一页后再过滤，这一页可能不足 size 条；`hasMore` 与游标仍然正确，翻页不会重复或遗漏。
