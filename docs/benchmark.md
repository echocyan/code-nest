# 压测报告

四个方案各压测一个场景，每个方案包含场景、目标、方案与取舍（链接到决策票）及压测数据。

> 压测在一台机器上完成，各容器限定了 CPU 与内存，k6 与被测系统共用宿主机。**数字只反映这套受限环境下的表现。**

## 测试环境

- **机器**：18 核、15G 内存，WSL2。
- **部署**：2 个应用实例，前面一个 Nginx 轮询；中间件 MySQL 8.4、Redis 8.6、RabbitMQ 4.3、Elasticsearch 9.4（IK 分词）。

  | 服务 | CPU | 内存 |
  |---|---|---|
  | 应用（每个实例） | 2 核 | 1.5G（`-Xmx1g`） |
  | MySQL | 2 核 | 2G（`innodb_buffer_pool_size=1G`） |
  | ES | 2 核 | 2G（堆 1g） |
  | Redis | 1 核 | 1G |
  | RabbitMQ | 1 核 | 1G |
  | Nginx | 1 核 | — |
  | k6 | 不限，用剩余的 CPU | — |

- **数据**：固定随机种子造数。10 万用户、10 万篇文章（已发布 94,851 篇）、500 万条关注关系、199 万条点赞、57 万条评论与回复；10 个大 V 各 2 万粉丝，100 个重度用户各关注 500 人。
- **方法**：每个场景先清空 Redis、重启应用；每轮先等 MQ 队列清空，预热 30 秒，再稳态压测 2 分钟，压测前后各采集一次 MySQL `SHOW GLOBAL STATUS` 与 Redis `INFO commandstats` 取差值（含后台任务的查询）。每个场景跑 3 轮，各项指标分别取中位数。压测时关闭限流。

## A 计数系统

**场景**：热门文章被大量用户同时点赞。每次点赞除了插入一行点赞关系，还要给文章点赞数、作者获赞数各加 1，这两行是所有点赞共享的热点行。

**目标**：点赞接口在高并发下保持低延迟；每个用户对同一篇文章至多点赞一次，计数最终与点赞行数完全一致。

**方案与取舍**（[计数系统决策票](../.scratch/code-nest/issues/06-counter-system.md)）：

- 瓶颈判断：点赞关系每次插入的是不同的行，不会争锁；会排队的是 `UPDATE article_stat SET like_count = like_count + 1` 这类热点行更新。所以关系表仍同步写库，只把计数移出事务。
- 业务模块在自己的事务里调用 `CounterApi.increment`，经 Outbox 发出计数事件，提交后投递到 MQ；counter 模块不依赖任何业务模块。
- 消费端用一段 Lua 在 Redis 里原子完成：Hash 或字段不存在返回 MISS（从 MySQL 懒加载后重试）→ 按 messageId 去重 → `HINCRBY` → 加入待落库集合。
- 每 5 秒 `SPOP` 一批待落库对象，把**绝对值**批量 `INSERT … ON DUPLICATE KEY UPDATE` 写回 MySQL；重复写结果不变，同一对象的多次变更合并成一次写入。
- 由掌握真实数据的模块每周对账，修正 Redis 与 MySQL。
- 取舍：放弃"计数与点赞在同一事务里强一致"，换来热点行不再排队；计数有秒级延迟；Redis 数据丢失时，尚未落库的增量（最多约 5 秒）靠对账补回。

**压测数据**：200 个 VU 用 200 个账号对最新发布的一篇文章反复点赞、取消。

- **正确性**：每轮压测结束、落库完成后，文章的 `like_count` 与点赞行数 `COUNT(*)` 相等（3 轮全部通过）。
- 文章点赞数、作者获赞数不再在 MySQL 里逐次更新：2 分钟内 8 万次点赞、取消，只有 2 次行锁等待。每次点赞或取消在 Redis 里累加文章点赞数和作者获赞数两个计数。

**压测中发现并修复的问题**：最初一版的结果是 QPS 499、P99 1406ms，行锁等待 2,100 次。给压测脚本加上各容器 CPU 与 `performance_schema` 语句耗时的采集后，发现并修复了以下问题（原始结果见 `results/` 与 git 历史）：

1. **重复计数**：一次点赞产生 3 条 Outbox 记录，每条 confirm 后单独 `UPDATE` 标记 SENT，高负载下标记任务积压在线程池里，应用重启时丢失，留下 7.7 万条 PENDING 记录。重启后补发任务重新投递它们，而消费端的 Redis 去重标记只保留 24 小时，计数被重复累加。修复：confirm 后只登记 ID，每 100 毫秒合并成一条 `UPDATE … WHERE id IN (…)`，应用停止前写完；创建超过 12 小时的记录不再补发，标记为 FAILED 并告警，约束消费端去重保留期必须长于它。`UPDATE` 语句从 4.5 万条降到约 700 条。
2. **计数事件合并**：同一事务里的计数变更在提交前合并成一个事件，点赞从 2 个计数事件变为 1 个，业务代码不感知。
3. **通知的唯一键冲突**：反复点赞时同一去重键的通知几乎都已存在，4.2 万次插入里只有 1 次成功；唯一键冲突时 InnoDB 对已有记录加共享锁并持有到事务结束，并发消费互相等待，累计锁等待 196 秒。修复：先用不加锁的普通查询判断是否已存在。行锁等待从 4,207 次降到 2 次。
4. **驱动往返**：每个事务前后的 `SELECT @@session.transaction_read_only` 比业务语句还多，开启 `useLocalSessionState` 后消失。

修复后 QPS 从 499 提升到 677（+36%），P99 从 1406ms 降到 820ms（−42%）。

**瓶颈诊断**：此时 MySQL 耗时最多的是 `COMMIT`（平均约 12ms，WSL 虚拟磁盘上 redo log 与 binlog 刷盘慢）。临时放宽刷盘（`innodb_flush_log_at_trx_commit=2`、`sync_binlog=0`）重测，提交耗时降为约 1.4ms，QPS 却没有变化（635，在波动范围内），说明瓶颈不在磁盘。RabbitMQ 在所有轮次都稳定在 0.92～0.96 核（上限 1 核），两个应用实例各约 1.6 核（上限 2 核），下一步应从这两处继续定位。诊断结果见 `results/2026-09-29-a-counter-relaxed-flush.json`，只用于定位，不作为优化手段。

## B Feed 推拉结合

**场景**：用户读关注 Feed。纯拉模式下，关注的人越多，读 Feed 越慢；纯推模式下，大 V 每发一篇文章都要写入几万个粉丝的收件箱，形成写扩散风暴。

**目标**：关注了几百人的重度用户读 Feed 首页依然快；大 V 发文不受粉丝数影响，普通作者发文后粉丝很快能看到。

**方案与取舍**（[Feed 推拉结合决策票](../.scratch/code-nest/issues/07-feed.md)）：

- 普通作者发文推送到粉丝的收件箱（Redis ZSet，上限 500 条），大 V（粉丝数 ≥ 5000）不推送，读 Feed 时从他的发件箱（最近 100 篇）拉取；两路合并、按文章 ID 去重倒序。
- 收件箱 TTL 7 天、读取时续期；推送跳过收件箱已过期的冷用户，用户回来时从关注的普通作者的发件箱重建，不需要另外维护活跃用户名单。
- member 与 score 都是雪花文章 ID，ID 本身就是分页游标；score 是 double，大 ID 舍入后相同的一组按 ID 精确比较，翻页不重复、不遗漏。
- 识别大 V 读 ZSet `feed:followers`（作者 ID → 粉丝数，关注、取关后按关注表重新统计）：一条 `ZRANGEBYSCORE` 取出全部大 V，再与关注列表求交集，不必逐个读取几百个作者的粉丝数。
- 作者升为大 V 时，已推送的文章留在收件箱，读取时去重；降为普通作者时，把他的发件箱并入全部粉丝已存在的收件箱。
- 关注、取关、删文时修正收件箱与发件箱，修正不到的残留在读取时过滤。
- 取舍：推送是异步的，发文到粉丝可见有百毫秒级延迟；Feed 最多往回翻约 500 条。

**压测数据**：200 个 VU 轮流使用 100 个重度用户（各关注 10 个大 V 和 490 个普通作者）读 Feed 首页；推送耗时是一个有 4999 个粉丝的普通作者（比阈值少 1）发文后，ID 最大（最后被推送）的粉丝读到这篇文章的时间。

|---|---|---|
| QPS | 816 | 796 / 816 / 819 |
| 平均延迟 | 244ms | |
| P95 | 809ms | |
| P99 | 1144ms | 1176 / 1144 / 1119 |
| 错误率 | 0 | |
| 服务端读一页 Feed 的平均耗时 | 224ms | |
| MySQL 查询 / 请求 | 2.05 | |
| MySQL 读取行数 / 请求 | 508 | |

| 推送 4999 个粉丝的耗时 | 160ms | 313 / 160 / 120 |

- 每个请求的 2 次 MySQL 查询是关注列表（走 (follower_id, author_id) 唯一索引的覆盖扫描，约 500 行）和列表项的分类；文章摘要、作者都从缓存读取。
- Redis 命令中，1 条 `ZRANGEBYSCORE` 识别大 V，约 11 条 `ZREVRANGE` 读收件箱和 10 个大 V 的发件箱，2 条 `MGET` 读文章摘要与作者，约 20 条 `HMGET` 读一页文章的计数。
- 大 V 发文不遍历粉丝，所以没有单独测大 V 发文的耗时：它只写一次自己的发件箱。

## C 搜索与数据同步

**场景**：10 万篇文章里按关键词搜索，要有中文分词和相关度排序；文章发布、编辑、删除后搜索结果要跟上。

**目标**：搜索延迟与文章总量解耦；结果按相关度排序、有高亮；文章变更秒级反映到搜索结果，旧数据不会覆盖新数据。

**方案与取舍**（[搜索与数据同步决策票](../.scratch/code-nest/issues/08-search-sync.md)）：

- 同步走 Outbox + MQ：search 模块收到文章事件后，经 `ArticleApi` 回查最新状态再写入或删除 ES，天然解决事件乱序。
- 以 `article.version` 作为 ES 外部版本号，旧版本的写入被 ES 拒绝，防止并发消费时旧数据覆盖新数据。
- 写入用 `ik_max_word`、查询用 `ik_smart`；`multi_match` 标题权重 3、摘要 1.5、正文 1，关键词与标签名一致时再加分。
- 索引经别名访问，全量重建时建新索引、切别名、按 `updated_at` 追补，搜索不中断；启动时别名不存在就在重建锁内执行一次重建，导入完成才挂别名。
- 取舍：不用 Canal，避免多部署一个中间件、也避免 search 模块依赖 article 的表结构；作者昵称和计数不进 ES，展示时再补全。

## D 多级缓存

**场景**：文章详情是读多写少的热点接口，访问高度集中在少数热门文章上。

**目标**：热点文章的读取不打到 MySQL，同时处理好缓存一致性，以及穿透、击穿、雪崩这三类问题；多实例下各实例的本地缓存能及时失效。

**方案与取舍**（[多级缓存与缓存治理决策票](../.scratch/code-nest/issues/09-multilevel-cache.md)）：

- 文章详情（元数据加正文，不含计数）用 Caffeine + Redis 两级缓存；用户、文章的批量摘要只用 Redis，批量读取走 `MGET`。缓存里不放计数，点赞不会让文章缓存失效。
- 业务代码只经 `TwoLevelCache` 的 `get`、`getAll`、`evict` 三个方法访问缓存，两级读取、空值缓存、布隆过滤器、TTL 抖动、失效广播都封装在组件内部。
- 一致性用 Cache-Aside：事务提交后删 Redis 并经 Pub/Sub 广播本地缓存失效，再由 MQ 消费文章事件做第二次删除，MQ 的投递延迟起到"延迟双删"的作用。
- 穿透用 Redis 8 原生布隆过滤器加 60 秒空值缓存；击穿靠 Caffeine 的同 key 合并加载，同一时刻落到数据库的查询数不超过实例数，不引入分布式锁；雪崩靠 TTL 加 0–5 分钟随机抖动。
- 取舍：热点 key 交给 Caffeine 的 W-TinyLFU 自然留存，不做专门探测；本地缓存以 60 秒 TTL 兜底 Pub/Sub 漏收。

**压测数据**：300 个 VU 匿名访问文章详情，候选为最新发布的 1000 篇，按 Zipf 分布（指数 1.2）抽取，前 10 篇约占 57% 的请求。

| QPS | 4,280 | 3,984 / 4,280 / 4,302 |
| 平均延迟 | 69ms | |
| P95 | 183ms | |
| P99 | 274ms | 476 / 274 / 273 |
| 错误率 | 0 | |
| `Com_select` | 5,656（0.011 次 / 请求） | |
| 文章详情的 Redis `GET` | 3,802（0.007 次 / 请求） | |

- 热点文章的详情几乎全部由各实例的本地缓存命中，不查 MySQL，也很少访问 Redis：51.6 万次请求只有 3,802 次读到 Redis。两个实例各有一份本地缓存，失效靠 Pub/Sub 广播。
- 每个请求剩下的约 6 条 Redis 命令是浏览量 +1 的 Lua 脚本（脚本内的 `EXISTS`、`HINCRBY`、`SADD` 各计一次）、读计数的 `HMGET` 和读作者的 `MGET`，都不随文章数增长。

## 关注列表缓存：30% 规则

**规则**（[压测方案决策票](../.scratch/code-nest/issues/12-load-test.md)）：如果查询关注列表的耗时占 Feed 读取耗时的 30% 以上，就加一层 Redis Set 缓存（关注、取关时维护）；否则不加。

**测量**：Feed 读取在服务端记两个 Micrometer Timer：`feed.read`（读一页 Feed 的全部耗时）和 `feed.read.follow-list`（其中查询关注列表的耗时）。场景 B 压测前后各读一次两个实例的累计值，取差值相除。

| Feed 读取平均耗时 | 关注列表查询平均耗时 | 占比（三轮） |
|---|---|---|
| 224ms | 4.7ms | 2.1%（2.1% / 2.1% / 2.1%） |

**结论：不加缓存。** 查询走覆盖索引，只要约 5ms，远低于 30%；加缓存要在关注、取关时维护一份 500 个成员的 Set，并处理缓存与关注表的一致性，收益不抵复杂度。

## 已知缺陷

以下是方案有意接受的取舍，压测中没有观察到，但需要如实说明：

- **长时间未发出的消息不再补发**：Outbox 记录创建超过 12 小时仍未确认（如应用长时间停机）时标记为 FAILED 并告警，不再投递，以免超出消费端去重保留期后被重复处理；对应的计数由每周对账修正，通知等其他事件需要人工处理。
- **计数 SPOP 窗口**：落库任务 `SPOP` 取出待落库对象后、写入 MySQL 前实例崩溃，这批对象的待落库标记会丢失，它们在 MySQL 中停在旧值，直到下次变更或每周对账时修正。Redis 本身开启 AOF everysec，Redis 宕机最多丢约 1 秒的增量。
- **对账 ±1 误差**：对账先 `GROUP BY` 统计真实值再 `reset`，两步之间如果有并发的点赞或取消，结果可能差 1，下一次对账修正。
- **Cache-Aside 竞态**：读请求未命中后从数据库读到旧值，写请求在此期间更新数据库并删除缓存，读请求随后把旧值回填。窗口极小，经 MQ 的第二次删除可以覆盖大部分情况，最坏情况持续到 TTL（30 分钟加抖动）过期。
- **Pub/Sub 漏收**：本地缓存的失效靠 Redis Pub/Sub 广播，不保证送达；漏收的实例继续使用旧值，最多 60 秒（Caffeine 写入后过期时间）。
- **大 V 判定可能短暂偏差**：`feed:followers` 在关注、取关后按关注表重新统计写入，两个消费者并发修正同一个作者时，后写入的可能是先统计出的旧值。只在粉丝数恰好跨过阈值时影响大 V 判定，到这个作者下次被关注或取关时纠正。
- **Feed 某一页少于 size 条**：收件箱里可能残留已删除的文章、已取关作者的文章，读取时截取一页后再过滤，这一页可能不足 size 条；`hasMore` 与游标仍然正确，翻页不会重复或遗漏。
